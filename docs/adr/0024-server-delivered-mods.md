# ADR 0024: Server-delivered mods

- Status: accepted (2026-11-05); built in the client and in the `photon-bridge` plugin of `photon-server`

## Context

[ADR 0006](0006-mod-platform.md) plans mods that servers deliver, and [ADR 0019](0019-photon-server.md) found that an unmodified Pumpkin lets a plugin send and read custom payloads only in the play phase, never in configuration. A server must be able to change items, the HUD, animations, sounds, pictures and physics, the client must fetch what it lacks once and read the cache afterwards, and Photon servers must be able to refuse players who are not on Photon.

## Decision

- **What the vanilla path carries.** Pictures, sounds, models, translations and item definitions travel as a server resource pack, whose push carries a hash; the client already keeps packs by hash and does not download one it has ([#51](https://github.com/PhotonMC/photon-client/issues/51)). Items with new looks and behaviour come from item components (`item_model`, `equippable`, `custom_model_data`), and physics from entity attributes (gravity, jump strength, step height, scale, speed) that the client already predicts with. Mods do not duplicate these; a server on a vanilla or Pumpkin base gets them with no Photon code.
- **What mods add.** Logic and screens vanilla cannot express: a HUD, sounds chosen by game state, custom client rules. A mod is a WebAssembly component run by `photon-mods` with the budgets of ADR 0006.
- **Play-phase channels.** The server sends `photon:mods` after the player joins: `{"v":1,"mods":[{"id","hash","size","url","caps"}]}`. `hash` is the SHA-256 of the file in lower-case hex, `size` is at most 8 MiB, `url` is `https` (or this machine, for tests), `caps` are the capabilities the mod asks for. The client answers on `photon:hello` with `{"v":1,"client","loaded":[ids],"refused":[{"id","reason"}]}`, once when it joins (nothing loaded) and again after each manifest has been processed. `refused` names each mod the client did not run and is left out when there is none; `reason` is one of `capability` (asks for a capability this client does not grant), `hash` (the bytes are not the named hash), `size` (not the named size), `fetch` (could not be fetched or kept), `load` (invalid code, or no room in the host), `consent` (the player has not allowed it), `stopped` (it was loaded, then trapped or ran past its allowance and was unloaded). A hello is also owed after mods are unloaded at runtime: its `loaded` no longer lists them and `refused` names each with `stopped`, at most one such hello per tick however many stopped. A mod stopped on this connection stays refused `stopped` when a later manifest lists the same id and hash; it loads again only when its hash changes or the player reconnects. A manifest that arrives while a fetch runs replaces the pending list: an answer for a mod the new manifest dropped or re-hashed loads nothing, and a hash already being fetched is not fetched twice. A manifest with any wrong entry is refused whole.
- **Cache.** Files are kept under `<game dir>/cache/mods/<hash>.wasm`. A file is read from the cache without any request when its hash is there and still matches its name (a changed file is a miss and is deleted); an update is a new hash, so a mod the server did not change is never fetched again. At most 128 files are kept, the least recently used go first (a read refreshes a file). Writes use unique temporary names, and temporary files older than a day are removed when the cache opens. Every fetched byte is checked against hash and size before it is kept, redirects are not followed.
- **Capabilities.** The client grants `events.tick`, `hud.text`, `sound.play` and `game.time` itself, since they touch only the game's own screen and sound or give a read-only copy of the level's clocks. `game.time` links two imports, `game-time` and `day-time`, each returning an `s64`: the level's game time in ticks as the server last set it, and the ticks of the dimension's own clock (zero without one), as of the tick that is running. These are the first state-reading imports; each further one is a capability of its own, copies data and never hands out references. The value they return is `photon_api::WorldView`, declared in `photon-api` beside the updater's plain values; the linker that exposes it is in `photon-mods`, and the WIT is generated from `photon-api`: see the addendum of 2026-11-12 on the mod interface. A mod is ticked only if it asked for `events.tick`. A mod that asks for anything else (files, network, player data) is not loaded until the client can ask the player; there is no such prompt yet. A mod cannot call an import it did not ask for, and its effects per tick are capped.
- **Unloading.** A new manifest unloads mods it drops or whose hash changed. A mod that traps or runs past its allowance is unloaded and the others go on. The mods end with the connection, which includes a configuration phase that runs again and a transfer: all mods are unloaded and the join hello is owed again, so the server delivers them anew (the cache makes that quick).
- **Photon-only servers.** `photon:hello` is the gate: a Photon-only server kicks a player whose hello does not arrive in a few seconds. It keeps vanilla clients out; it is not a security boundary, since anyone can send the payload.
- **Physics.** Stays server-authoritative. The client mirrors it through attributes and the movement it already predicts. A mod does not move the player itself, or the server's corrections would undo it.

## Consequences

- A server delivers mods after the join, so the first seconds of a join run without them.
- The server side (sending the manifest, the hello check) is the `photon-bridge` plugin in the `photon-server` repository, built against Pumpkin's plugin interface 0.1.0. That interface has no channel in the configuration phase and no timer finer than a server tick, so the manifest goes out after the join and the hello check runs every few ticks.
- Signing is still open (ADR 0006). Until it exists, a manifest is trusted exactly as far as the connection to the server is, and the hash only guards the file against the host that serves it.

## Addendum (2026-11-06): live-test notes and consent

`item_model` naming a registry item works live, definition ids that exist only in a pack (`items/<namespace>/<name>.json`) work live too; an id nothing defines draws the missing model (a full cube with the missing texture on every face), checked live (a cube in the hand, the missing texture in the hotbar), not yet against Java

Capabilities that touch the player's machine or data (first `fs.mod_data`) need a prompt before the mod loads. The prompt shows the server name, the mod name, its hash and the capability, and the answer is remembered per server and mod hash. Game-local capabilities load without a prompt.

## Addendum (2026-11-12): budgets, limits, cache, consent

All mods together get 4 ms of each client tick (ADR 0006 gives no total); the per-mod allowance stays 20 ms, so one overrunning mod can pass the total by up to that much before it is stopped and unloaded. Mods that did not get to run wait and run first in the next tick, in a fixed turn order, and keep the text they last drew meanwhile. At least one mod runs every tick.

Compiling a mod (the slow part of a load) runs on the fetch thread with the shared engine; only instantiating it, which takes a pool slot and runs the start function under the allowance, happens on the game thread.

Limits per mod, beyond the 16 MiB of memory: 20000 table elements, at most 4 memories, 4 tables and 16 core instances per component, 512 KiB of wasm stack, 1 MiB of bookkeeping per instance (deep recursion traps as `stack overflow` and unloads only that mod). A load past the pool of 400 mods fails with an error naming the limit.

Consent, as built without a screen: the answers are kept in `<game dir>/mod_consent.json`, a record per (server, mod hash) with the capabilities granted and refused, replaced atomically. Only `fs.mod_data` needs an answer today; any other capability the client does not grant refuses the mod (`capability`). A mod that needs an answer is held back (not fetched) and is named in the hello as refused for `consent` until the player answers; a grant fetches and loads it, a refusal keeps it refused, and a refusal remembered for that server and hash refuses it again without asking. A granted `fs.mod_data` links three imports: `data-get(key: string) -> option<list<u8>>`, `data-set(key: string, value: list<u8>) -> u32` (0 is success; 1 bad key, 2 value too large, 3 store full, 4 too many writes this tick, 5 no store) and `data-delete(key: string) -> bool`. The store is per server and mod id, in `<game dir>/mod_data/<server key>/<id>.bin` (the server key with anything but letters, digits, `.` and `-` turned into `_`), so it survives reconnects and a mod update (another hash, the same id). Keys are 1 to 64 printable ASCII bytes, values are at most 64 KiB, a mod keeps at most 1 MiB (keys and values), and a tick may make 16 writes (sets and deletes). The store is read when the mod loads (one file of at most 1 MiB, on the game thread, outside any tick) and lives in memory; what changed goes to a writer thread at the end of the tick, which replaces the file atomically (a temporary file renamed over it), keeping only the latest of queued changes per file, and dropping the runtime writes what is queued. A damaged file starts the mod with an empty store. The client links the import only for a mod whose `fs.mod_data` the player allowed. The key is the address the player connected to, as lower-case `host:port` (the name the player used, else the IP; after a transfer, the address it was sent on to), which the net session carries through login, reconfiguration and transfer. The prompt is Photon's own notice screen over the dimmed game, one per mod, queued: it names the server, the mod id, the first 12 characters of the hash and each capability, with Allow and Deny (Escape denies; the buttons wake after a second so a stray click does not answer). It opens when no other screen is up, lets the mouse go as any screen does, and does not pause the game or the connection. The answer is kept per server and mod hash, as above.

A fetch whose file the latest manifest no longer waits for stops before its request and between 32 KiB chunks of the body, keeps nothing, and is started again only if a newer manifest wants the file after all.

`player.state` (2026-11-12) is the next read-only capability, granted without a prompt like `game.time`: the mod's tick may call `player-x`, `player-y`, `player-z` (f64, the feet, in blocks), `player-health` (f32, half hearts) and `player-yaw` and `player-pitch` (f32, degrees), which read a copy (`PlayerView` in `photon-api`) taken at the start of the tick, zeros until the player exists. Not built, because each needs a decision first: `events.frame` (a per-frame call needs its own budget at frame rate and a payload), `input.keys` and `chat.read` (they show the player's keys and messages to a server's mod and need their own consent), and `registry.read` (which registries, and by which ids).

The mod interface (2026-11-12): `photon_api::IMPORTS`, `EXPORTS` and `CAPABILITIES` declare every host function (name, parameters, result, capability, doc) and the export `tick` once; `photon-mods` links its imports by iterating that table (a capability that is not granted defines nothing, as before) and its tests load a component per entry with the declared signature. `cargo xtask gen` writes `crates/photon-api/wit/photon-mod.wit` from the same tables (`--check` fails when it is stale); that file is the reference for the capability to function mapping and for writing a guest. Package `photon:mod@0.1.0`, chosen here because no ADR named one. The names stay root-level functions (`hud-text`, not an interface), so deployed mods keep loading. Each capability is a world (`cap-hud-text`, ...) and `photon-mod` includes them all; a guest's own world includes the capabilities it asks for. Building a guest against `photon-mod` also works, because `wit-component` leaves unused imports out of the component, but a guest should include only what it asks for. The host requires the export `tick` of every mod, even one that did not ask for `events.tick`. An example guest is `examples/hello-mod` of `photon-server`.
