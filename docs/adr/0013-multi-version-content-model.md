# ADR 0013: Multi-version content model

- Status: accepted (2026-10-28); replaces the version packs, extractor and translation layer of [ADR 0004](0004-version-support.md)

## Context

[ADR 0004](0004-version-support.md) planned several supported versions through generated data packs, an extractor run against each version's jar and a protocol translation layer. None of it was built. The generated tables in `photon-data/src/generated/` cover one version, and the extractor would be a second tool to keep correct for every release.

The goal is unchanged: one client that joins servers of the newest version and of a few older ones, with the newest version held to full parity.

## Decision

- **One binary, no launcher.** The version is a runtime value, chosen at connect time from the protocol number in the status ping. A per-server manual override in the server list can follow later. There are no cargo features per version.
- **Union content model.** Behaviour defaults to the newest version. Content (blocks, items, entity types, sound events, particle types, menu types and so on) is the union of all supported versions. Content that a newer version removed stays defined with `until(..)`; it is never mapped to a "closest" replacement, because that breaks parity.
- **Code, not data.** Version differences are Rust code. There are no per-version data packs and no extractor. The generated tables are a transitional state and move to hand-written definitions.
- **Two id spaces.** Game code uses canonical ids: the index in the union list, known at compile time, so `named(..)` constants keep working. Wire ids are per version and exist only at the protocol boundary, as separate types (`WireItemId`, `WireBlockStateId` and so on). A per-session `VersionRegistries` (`photon_data::version_registries`; the name keeps it apart from the server-sent data registries of `photon-game`), built once at connect, translates between the two.
- **Ids are computed, not stored.** A version's wire ids come from walking the union list filtered to that version, the way the block registry already numbers states: registry order, cartesian product of properties, last property fastest. A property added in a newer version carries `since(..)`; older versions map its states to the property's default value.
- **Availability.** `registries.has(x)` filters every list the client builds itself (creative tabs, recipe book, command suggestions), as the reference's feature flag set does.
- **Where differences live.** Each crate has a `versions/` module with one file per older version (for example `photon-world/src/versions/v26_1.rs`). Canonical code never names an older version.
  - Behaviour differences go through a `Rules` trait with canonical defaults and per-version overrides: generic dispatch, chosen once per session, for hot paths; `dyn` for cold ones.
  - Replaced systems are swapped by name in a per-version schedule builder, which needs the named system sets of [#165](https://github.com/PhotonMC/photon-client/issues/165).
- **Lint.** `Version` comparisons appear only in `versions/` modules and in a short list of dispatch points. Wire id types appear only in `photon-protocol` and `photon-net`. Wrapping a raw read into a canonical id outside the translation point (`ItemId(read_varint(..))`) is an error.
- **Support window.** The newest version plus the two before it. Dropping a version deletes its `versions/` modules and its `until` definitions.
- **Second version: 26.1**, chosen to test the design cheaply ([#17](https://github.com/PhotonMC/photon-client/issues/17)).
- **Verification.** Java stays a development-time reference only. Each version gets a registry order case, a definition properties case, and a difference table with a case for every override. As in ADR 0004, older versions are held to parity of their difference table; the newest version is held to full parity.

## Consequences

- The ADR 0004 decisions on version packs, the extractor, `cargo xtask gen <version>` and `photon-protocol::translate` no longer apply. Its one-branch rule, the canonical newest-version model, selection at connect time and name-based id resolution stay.
- The work is split into the version skeleton ([#161](https://github.com/PhotonMC/photon-client/issues/161)), the registry order case ([#162](https://github.com/PhotonMC/photon-client/issues/162)) and retiring the generated tables ([#163](https://github.com/PhotonMC/photon-client/issues/163)). Until they land, protocol 776 is the only version.
- A version costs hand-written definitions and an override per difference. In exchange there is no data format to maintain and canonical code stays free of version checks.
- The lowest supported version is bounded by the window, not by the availability of mappings.

## Addendum (2026-11-06): support window and generators

- **Window.** The supported window is Java Edition 1.21.x up to the newest version. It replaces "the newest version plus the two before it": players join any Java server, and many servers run older releases. The floor is the oldest 1.21 release. Releases that share a protocol number are one `Version`; the protocol numbers come from each release's `version.json`. The owner can move the floor.
- **Generators.** The "code, not data" bullet no longer holds for the reference tables in `photon-data/src/tables/`. They are produced again by generators under `xtask` (`cargo xtask gen`), committed with an `@generated` header and never edited by hand. `cargo xtask gen --check` regenerates them and fails on any difference.
 
- **Behaviour differences, interim state.** Version differences in behaviour belong in `versions/` modules behind a per-session rules value. Today game code asks named questions in `photon-core/src/versions/behaviour.rs` (`punch_is_swing()`, `pose_rotates_by_quaternion()` and so on), and those still read the process-global `Version::active()`, set at connect. That is an interim seam: one process holds one version. The `version-compare` lint now flags every read of the version (a full path, `Version::active()`, `active_before_*`), so a new read outside a `versions/` module or a listed dispatch point fails. The oracle asks through `photon-oracle/src/case_ids.rs` only. Still owed: call sites that already have a session (the container code, the game mode) take the value from it, and the predicates take a rules value instead of reading the global.
- **Oracle sources.** Java oracle classes whose text is identical in every version live in `tests/behavior/java/common/`; `v<tag>/` keeps the differing ones. The remaining differing files mostly differ by input type construction (`SdlInput.key` against `KeyEvent`); moving that behind an `Access<ver>` seam, so the files collapse into `common/`, is owed.


## Addendum (2026-11-06): switching the version inside the client

- **Requirement.** The player picks the game version inside the client, and the result is indistinguishable from a fresh process started on that version: no loading screen, no stale state, behaviour of that version. The same-process test is the bar: parity for two versions run in one process with a switch between them (and back) must equal separate runs byte for byte.
- **When.** A switch happens only while no play session runs (title screen, server list). A connection speaks one protocol, so a switch mid-session is a disconnect; with no world loaded no worker reads shapes or registries while the active version changes.
- **State.** Version-dependent statics are keyed by version (one slot per `Version`, indexed by `Version::index()`), never reset, so there is nothing to invalidate and switching back is free. The process-global active version stays the interim seam above; it is only written between sessions.
- **Assets.** Each version has its own asset root and asset index (an `assets_for(version)` resolver and a per-version index table replace the hard-coded numbers). Content of the target version (atlases, fonts, sound, language) is built on a background thread while the menu stays live, then swapped at a frame boundary; the build starts when the picker opens, so the switch shows nothing to wait for. A version whose assets are not on disk cannot be picked.
- **Picker and server list.** The server list ping reports the protocol; the ping-driven version is the default for joining a server and the picker is an override that sets the version of the next join. (Owner-reversible decision.)
- **Honesty.** A switch working is separate from a version behaving as that version: the 26.2 run still differs from the Java client in 84 cases, and 1.21.x versions wait for their jars.
- **Implemented so far.** `content_root::assets_for(version)` finds `jar-<version>` (or `jar` when its `version.json` names the version) beside the start-up assets folder and `select_version` makes it the folder every reader sees; `setup` extracts each version into `jar-<id>` and the newest also into `jar`. A join selects its version's assets, builds a fresh resource stack for them and bakes the block atlas again when it came from another folder; the bake is started on a worker the moment a connection has its version (or the player picks one), so the join finds it ready. The home screen has a button that cycles automatic and each version that has assets. `cargo xtask parity --switch 26.2,26.3` is the same-process check: one Rust adapter process answers each version's cases in turn, twice around, and every answer must equal a fresh process's.
- **Still owed.** The version-dependent statics outside the oracle needed no change (the registries are keyed per version and the rest is canonical), but the process-global active version is only written between sessions; a per-session rules value replaces it. Measured on a local join (release build): the blocks bake ahead; the rest of the game start of the new session takes about half a second (entity textures ~110 ms, audio ~60 ms, GUI with fonts and language ~225 ms) and runs behind the join's own network wait, where the player sees no extra screen. Baking those ahead too would shave that half second but needs the session's registries and options; it is owed only if a join on a fast server shows it.
- **Live check, 2026-11-06.** One client process (`photon menu`, `PHOTON_HOPS`) joined a 26.2 server, a 26.3 server and the 26.2 one again, each leaving through the pause path; every join took its version's assets (3987 models for 26.3, 3723 for 26.2) and ran its 61 scripted ticks with chunks and entities, with no error. A start-up folder that names another version no longer stands in for the newest one (it played 26.3 with 26.2 assets). The installer's pin (`photon-content` `PINNED`) now follows the newest version (26.3, jar digest from `tests/behavior/reference/26.3.json`), so an installed game plays the newest version; older versions need their own assets folder beside it.
- **26.2 behaviour found by the parity run, 2026-11-06.** 84 differences at the start; 80 after this round. Fixed: the resource pack headers a server sees (`X-Minecraft-Version`, pack format 88.0 for 26.2, 97.1 for 26.3) and the F3 version name follow the played version (`versions/behaviour.rs`); 26.2 block models read the boolean `shade` (false lights the element as the top face), read by the version of the assets being baked, not the one played, because a bake ahead runs while another version is active (`with_asset_version`). The window's minimum size stays 320x240 for every version, since the window opens before a version is chosen and is not recreated by a switch; the oracle reproduces 26.2's minimum of 1 for parity only (owner may reverse). Still owed, by family: armor trims (26.2 names one picture per pattern and material, 26.3 recolours one by a palette), the wire decoders that accept a negative count (update tags, custom chat completions), the screen layouts of the option screens, creative tabs and item components, the model quads of the player, zombie, skeleton, piglin and dragon, glint blend, and the movement rows listed in the #225 comment.
